# Multiple Named Detectors — v0.3 foundation

This increment introduces a pure-logic path from one captured frame to multiple named GameState observations.

## Data flow

```text
frame
  ↓
DetectorRegistry
  ├─ collect_button
  ├─ continue_button
  └─ inventory_full
  ↓
Detection[]
  ↓
apply_detections(...)
  ↓
GameState
```

No keyboard or mouse input is generated by this path.

## DetectorSpec

Each named template detector has:

- `name` — stable GameState key
- `threshold` — OpenCV template-match threshold
- optional `roi=(x, y, width, height)`

ROI matching returns bounding boxes translated back into full-frame coordinates, so downstream state/rules do not need to know whether a detector searched the whole frame or a cropped region.

## DetectorRegistry

`vision.detector_registry.DetectorRegistry` owns multiple independent `TemplateMatcher` instances.

Important behavior:

- duplicate detector names are rejected
- every registered detector produces one result per cycle
- missing matches become explicit `visible=False` detections
- registry changes are protected by a lock
- detection itself is side-effect free with respect to input control

## GameState bridge

`agent.vision_state_bridge.apply_detections` writes one detector cycle into `GameState`.

All observations from the cycle receive the same monotonic timestamp. Duplicate names in a cycle are rejected before any state mutation, preventing accidental overwrite ambiguity.

## Current limitation

The existing Tkinter application still uses the original single-template UI path. This increment deliberately does **not** modify `main.py`.

The next integration step is to load/configure multiple detectors in the live capture loop, then let Claude smoke-test that Windows behavior before autonomous input is connected.
